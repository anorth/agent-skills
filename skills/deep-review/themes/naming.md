# Naming

Always load. Identifiers: fields, methods, types, config keys, packages, files.

## Guidance

- **Name for the exact thing, not a nearby thing.** Pick the precise domain role, subject, property, or quantity: which subset, which participant (source/destination/replacement), which lifecycle stage (pending, verified, snapshot, current, historical), signed delta vs. baseline vs. target. Reject names borrowed from an incidental workflow step, or terms reused for a different underlying concept. Make units explicit, especially in constants and at API boundaries, and never reuse a name/type implying a dimension (e.g. weighting) the value does not carry.
- **The name must cover the method's complete actual behavior**: results, side effects, direction, and cost. Aggregate-returning methods should reveal the scope computed and that a whole-collection walk is expensive. Use retrieval verbs like `fetch` for possibly slow/network-backed work vs. local lookup; action verbs for mutators and predicate names only for side-effect-free checks; state names for the specific terminal transition performed. Collection mutation names should say whether they deduplicate, mutate in place, or copy; iterator/cursor helpers should convey advancement; destructive operations should make deletion, reset, abort, or enforcement explicit.
- **Delete context the enclosing scope already supplies** — package, type, module, builder, product, or filename. Don't give a type the same name as its package, and keep package declarations consistent with import paths. Locals near first use can be short; exported members need enough detail to express their role standalone.
- **One term per concept, everywhere.** Use a single established, semantically precise word across code, docs, comments, error messages, and user-facing text; keep analogous fields, parameters, and operations on the same term; use symmetric parallel names for paired APIs and lifecycle operations; pick one conventional term for sentinel/absent values. When renaming, update comments, docs, aliases, and related identifiers in the same change, and rename when historical terminology no longer describes the concept.
- **Make collections and mappings self-describing**: contained entity type, state, lookup direction, and the relationship being indexed. Plural for multi-item parameters and collections, specific singular for elements, and distinct names for single-item vs. bulk operations.
- **Booleans read positively**: `true` should directly state the enabled or tested condition. Name aggregate flags for the condition they literally represent, not for an inference drawn from it.
- **Keep identifiers distinguishable from what they identify.** Id and reference fields should not read like the object or data itself; name id parameters after the identity system or identifier kind; make it clear when a function returns an id, an address, or a relationship rather than a value.
- **Name at the abstraction's own level.** Expose the broad concept or responsibility, not an implementation detail, backing source, or one caller's domain; name dependencies, callbacks, and handlers after the generic capability, role, or event; size shared abstraction names to cover intended scope and likely future variants. Conversely, avoid vague filler labels — components, packages, and helpers get their specific substantive responsibility.
- **Avoid overloaded, ambiguous, or misleading terms** when established concepts already own a meaning, and keep distinct terminology for related concepts that are easy to conflate. Don't name a mechanism as an exceptional fallback if it is the normal path.
- **Don't ship names that describe nothing**: helpers whose name only announces an absent option, an empty wrapper, a redundant convenience, or obsolete behavior, and aliases implying encoding or capability that isn't supported.
- **Get public names right before they stabilize**: accurate, appropriately narrow, free of unstable version-specific tags, with implementation-only helpers unexported. Where versioning is real, apply clear and consistent version identifiers across commands, constants, structures, migrations, and fields, and preserve established cross-module names when relocating a concept.
- **Time and validity names state what they measure.** Delays, intervals, timeouts, and time fields name the event, condition, unit, or progress state; expiration and boundary conditions make inclusive/exclusive semantics unambiguous; time-dependent values say which point in time they represent when a current-period variant could exist.
- **Optimize for readers scanning similar names**: make the distinguishing token visually prominent, avoid opaque abbreviations for return values, channels, and primitive arguments, destructure tuples into meaningful names, and don't shadow a parameter with a pattern-bound local. Concise generic names are fine for structured parameter objects when context supplies the meaning.
- **Separate inputs from outputs in the type system's names**: distinct types for operation inputs and results, input structures named after the operation they parameterize, constructors named for the abstraction they actually create with name, return type, and doc aligned.
- **Config keys name what they control** — the behavior, purpose, timing, ownership, resource, or entities affected — not how the value is consumed.
- **Use grammatically correct noun phrases for types and completed results**; name synchronization primitives after the condition callers wait for or that they signal; name externally visible events after the user-relevant state transition.
