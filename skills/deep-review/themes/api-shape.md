# API Shape

Reviewing the surface a change exposes: function and method signatures, interfaces, types and identifiers, return shapes, serialized/wire schemas, and the boundaries between layers. Load this for any diff that adds or changes a public function, interface, type, endpoint, event, or persisted format.

## Guidance

- **Minimize the exposed surface.** Public interfaces should express consumer-facing capabilities only; keep implementation detail, internal lookup helpers, subsystem-specific identifiers, test-only constants, and test-double internals private. Expose only the data relevant to a structure's purpose, only the return values callers actually use, and only the specific context values a consumer needs rather than a broad request/message/context object. Don't widen production APIs, or add methods to shared foundational types, for hypothetical generality — wait for repeated real use.
- **Every parameter must be necessary and non-derivable.** Drop parameters whose value is derivable, already available through construction or runtime dependencies, unused, or added only to improve an error message; propagate any configuration that is currently accepted and ignored. Pass the smallest, narrowest value a helper needs — not a container plus a derived view, not a whole object when one field suffices.
- **Conversely, every input that affects the result must be explicit.** Computation APIs must accept all inputs influencing their output; creation APIs must accept and propagate all required fields; state-dependent reads should take the state snapshot or version they read against; verification APIs should take their verification inputs (including algorithm/format identifiers) rather than inferring them; caller-supplied bounds, deadlines, and timeouts belong at the operation boundary. Behavior-affecting parameters should be explicit and descriptively named, never implied.
- **Consolidate duplicate entry points.** Prefer one canonical parameterized operation plus, only where it truly reduces caller complexity, thin convenience wrappers for common defaults. Retire redundant legacy variants rather than accumulating them; don't add wrappers that merely bind a constant argument, rename a builder, or duplicate an existing canonical conversion; don't expand deprecated APIs — point callers at the replacement.
- **One canonical representation per concept.** Use the same domain type, numeric type, and identifier form across APIs and stored state; reference the authoritative definition instead of restating a matching constant or re-deriving an equivalent type. Return and compare canonical identifier values directly when richer wrappers add nothing; keep semantically distinct identifiers and roles in separate fields or role-specific types; avoid storing an identifier that a map key already supplies; maintain a single authoritative copy unless duplication has a stated purpose. Design around the representation callers naturally hold, and normalize/convert at the lowest boundary. If a library already owns the type or constant, use that rather than a local copy.
- **Wrappers and abstractions must earn their existence.** Remove types that add no semantics over the underlying value, single-field parameter wrappers, redundant key or primitive wrappers, name aliases for primitives, redundant equality helpers, and pass-through layers. Do add semantic value types that encode units, distinct types for distinct semantic states or lifecycle boundaries, and extensible records where a primitive mapping will need to grow.
- **Return cohesive results.** Group one operation's related outputs into a single result object or type; return newly assigned identifiers from creating operations; report lookup presence separately from the value; don't return a value the caller passed in, and don't return both a composite and its contained part unless both are independently needed. Don't expose a fallible channel for an operation that cannot fail, and avoid signaling failure through two mechanisms at once.
- **Model absence and modes honestly.** Encapsulate optional/sentinel handling behind reusable types; prefer an explicit null or optional over a zero/sentinel meaning "absent" (and document any sentinel that must still pass validation); use empty collections rather than optional collections for "no results"; make an enum's zero value an explicit unknown/unset; avoid nested optionals. Replace ambiguous booleans with named constants, distinct types, or separate operations, and model distinct operation modes explicitly instead of an ignored or overloaded parameter.
- **Bound anything that can grow.** Historical or large collection reads need pagination, ranges, cursors, or scoped traversal; paginated responses must state explicitly when no items remain; cursors should be opaque and validated internally. Provide narrow single-item reads instead of copying whole collections, and bulk operations for repeated independent updates while keeping an efficient single-item path. Bound network traversal and fetches with a timeout or an explicit size limit.
- **Document what the signature can't express:** exact byte/wire format of opaque inputs, units and normalization bases, observable ordering, range endpoints and traversal direction, iterator exhaustion rules (make exhaustion explicit and checkable), batch output alignment and per-item failure markers, async completion/closure guarantees, whether identifiers are normalized, and no-op semantics (deleting a missing key, empty input, zero values). Document invalid inputs as preconditions instead of silently masking misuse; don't document invariants the interface cannot enforce.
- **Signature ergonomics and consistency.** Order parameters by primacy and natural data order, put the common operation first, and keep field order, parameter conventions, and structural shape consistent across analogous APIs. Use a parameter/result struct for high-arity operations where named fields aid evolution; don't introduce one for two or three values with no benefit. Use plain parameters and direct returns for in-process abstractions; use package-level functions when no receiver state is needed.
- **Constructors should produce valid objects.** Require the configuration that is genuinely essential (delegating to simpler constructors), distinguish creating fresh state from loading existing state, keep I/O out of constructors in favor of explicit initialization or factories, don't offer default construction when there is no valid default. Inject clocks, stores, IO, and environment-derived configuration through constructor parameters or interfaces — not package globals, hard-coded hosts, or ambient state — and thread the same instance. Grouping a long dependency list into a config/deps struct is preferred over a growing positional list.
- **Configuration and defaults.** Provide sensible defaults with an explicit override path; require explicit configuration where a default would likely be wrong; choose new defaults that preserve existing behavior. Expose behaviorally significant knobs (and hard-coded limits that need to vary) instead of hard-coding them, export constants callers must configure against, and offer one canonical configuration API per option — with defaults centralized rather than restated at each call site.
- **Layer deliberately.** Keep low-level interfaces primitive and compose higher-level behavior above them; separate computation from policy and context; split operations with different responsibilities and preconditions, but combine methods that are never usable apart. Expose derived values from the component that owns the calculation, and encapsulate recurring multi-step sequences (construction, serialization, cache-miss load, decode, request/response) behind one helper when callers keep repeating them. Prefer small orthogonal composable APIs over broad convenience interfaces; flatten an interface when it makes alternative implementations and test doubles simpler.
- **No test-only APIs on the production surface.** Don't widen production APIs or add accessors, harness methods, or constants that exist only for tests. Give assertion and setup helpers every semantically distinct input they need, avoid hidden magic defaults, return what the caller must assert on, and let test-double constructors take required initial state. Keep test helpers local or behind public configuration — not new core methods that require internal access.
- **User-facing surfaces follow the user's model, not the internals.** Shape endpoints and commands around the information the caller has and the action they intend — name creating operations after the action and return the new location/identifier, place commands under their resource namespace, keep flat and discoverable, keep descriptions consistent with actual defaults, make output readable by default with detail opt-in and a machine-readable mode for scripting, and use stable public identifiers in URLs.
- **Event and notification payloads:** carry exactly the fields consumers require — including state they would otherwise have to reconstruct and the participant identifiers they filter on — without duplicating ambient metadata or leaking debug-only internals; omit absent optional attributes instead of emitting nulls; emit on meaningful state transitions rather than preparatory steps.
