# Comments & Documentation

Always load. Comments, docs, and nearby comments the diff makes stale.

## Guidance

- **Verify every comment against the code it sits next to.** Check control flow, data flow, formulas, declarations, conditions (including negation and boundary/flag semantics), and names actually match. A comment that was true before the diff and is now stale is a defect; flag it even when the diff didn't touch that line. Documentation that asserts an invariant the change invalidates must be updated or deleted.
- **Require TODOs to be actionable.** Concrete deferred work, cleanup, or optimization should name what remains and link a tracked issue; reject vague "TODO: fix this later", TODOs whose work is already done, and searchable-marker-free prose about unfinished work. Prefer documenting the current limitation plus a link over an open-ended placeholder.
- **Demand purpose, not paraphrase.** Comments should explain intent, responsibility, and why the code is correct — not restate what the next line obviously does. Cut redundancy with shared helpers and established conventions. Prose should be concise, grammatical, and unambiguous; long hedging, historical asides, and disclaimers outside the component's actual responsibility are noise.
- **Public surfaces need a contract.** For exported types, interfaces, functions, macros, wrappers, and constructors: purpose, intended use, preconditions, authorization/caller scope, effects, return values and their variants, sentinel/partial outcomes, errors, and what the caller must guarantee. Describe externally observable effects and state transitions rather than internal storage or upstream assumptions.
- **Non-obvious values must carry their meaning.** Constants, limits, defaults, coefficients, units and scales, formulas, enum/sentinel/placeholder values, optional fields with special absent semantics, and encoded fields: state the meaning, the source, the resource or trade-off being protected, and the comparison or entry point that makes the value meaningful.
- **Explain the reasoning that makes non-obvious code correct.** Algorithms, lookups, filtering, aggregation, ordering, state transitions, concurrency and re-entry constraints, initialization order, deliberate nondeterminism or tie-breaking — document the assumption or safety argument, not the mechanics.
- **Data shapes need documenting.** For non-obvious structures, fields, and collections: contents, keys/indexes, ordering and positional semantics, gaps, mutation behavior, lifecycle, invariants, and whether state is durable or in-memory/transaction-scoped only. Refer to data by the named abstraction that defines it, not an inferred underlying representation.
- **Temporal semantics must be explicit.** Snapshots vs. live reads, intervals, deadlines, validity windows, retention, current vs. previous period, and lifecycle boundaries.
- **Intentional deviations require a rationale.** Omissions, shortcuts, fallbacks, defensive checks, workarounds, compatibility and migration paths, temporary bypasses, and disabled code or tests: record why it's safe, its limitations, the tracking issue, and the concrete condition for removal or re-enabling.
- **Preconditions must be stated at the enforced strength.** Don't claim constraints the code doesn't enforce or that a spec/standard is fully implemented; document delegated guarantees, boundary cases, expected failures, and deliberate deviations honestly.
- **Keep documentation adjacent and single-sourced.** Place each comment on the declaration it explains; keep one authoritative location rather than duplicating interface docs on implementations (unless the implementation adds behavior); generate repetitive API/default-value docs from metadata where practical; carry doc-comments along during moves and refactors.
- **Use precise, consistent terminology.** Define ambiguous terms, quantities, boundaries, and state-transition outcomes; name the responsible component or party explicitly instead of "we"/"the system"; don't apply blanket terminology rewrites where the original wording was behaviorally accurate.
- **Test code deserves accurate documentation too.** Explain what a fixture, double, fault injection, or simulation does and doesn't model, its parameters and expected behavior, and how to regenerate or run it. Non-obvious regression tests should name the failure mode they prevent. Keep test comments limited to the state and values relevant to the operation.
- **Prefer extraction over explanation.** When a comment exists only to explain the structure of a cohesive block, or to name a condition, ask for a well-named function or predicate instead.
- **Document configuration, build, and tooling behavior** with supported conditions, concrete paths, assumptions, rationale, consequences, and an example where the invocation is non-obvious.
- **Remove obsolete, speculative, or completed comments and markers**, but preserve enduring rationale, provenance for copied code, historical identifiers, and external spec references that compatibility or maintenance still depends on.
- **State the concrete failure a fix addresses** in the change's own documentation, and document intentional differences between related entry points or versions so callers know which behavior applies.
