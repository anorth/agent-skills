# Coupling and Dependency Direction

Scope: load when reviewing diffs that add or change module boundaries, shared helpers/constants/types, dependency wiring, or public APIs between components.

## Guidance

- **Collapse repeated operational logic into one established helper or abstraction.** If a diff re-implements a sequence that already exists elsewhere (parsing, threshold/predicate math, loading a shared structure, a state transition), route it through the existing construct rather than duplicating or bypassing it with lower-level manipulation.
- **Depend on narrow, consumer-defined interfaces, not concrete implementations.** The dependency should be the smallest surface the caller actually uses, so it can be swapped and tested with a trivial fake. Represent cross-component requirements as capabilities/interfaces rather than a concrete type or identity, and drop parameters a helper no longer needs.
- **Pass the explicit values an operation needs.** Avoid threading broad ambient context or whole input/internal structs to reach one field; expose only the stable fields or derived data consumers need. Pass already-loaded data into helpers instead of reloading, and compute a derived value once rather than in each helper.
- **Respect layering direction.** Generic, reusable, and low-level layers (data structures, storage, runtime/platform, validation libraries, test/emulation infrastructure, specifications) must not depend on higher-level applications, application-specific policy, execution contexts, persistence types, or fast-moving implementations. Push policy, validation, scheduling interpretation, and feature-aware lookups upward, or inject them through narrow interfaces; return errors to callers instead of reaching into a runtime.
- **Cross component boundaries through the owner's public API.** Do not inspect or invoke another component's internals, and route state changes and destructive lifecycle actions through the component that owns the resource so its invariants stay consistent. Don't expose APIs that leak another component's implementation type or internal identity, and don't surface low-level resources from a high-level provider for caller convenience.
- **Adapt at the boundary.** When independently evolving components model the same operation differently, add an explicit translation/adapter layer; wrap third-party interfaces in project-owned abstractions where that aids reuse, testing, or upgrade isolation; classify runtime/environment-specific faults at the boundary rather than in business logic. Keep shared orchestration APIs independent of component-specific payload shapes.
- **Derive from authoritative current state.** Prefer the object's own current state or the persisted/authoritative source over cached, transformed, reconstructed, or order-dependent values; determine version/identity from the artifact itself rather than from the running caller. Avoid extra cross-component calls when the local operation's result already carries the needed data.
- **Keep narrow APIs narrow.** Resist convenience methods that drag a larger abstraction into a low-level plumbing layer, thin auxiliary types that add coupling without abstraction, and versioned wrappers where a stable lower-level abstraction suffices. Keep storage-specific compact encodings and backend-specific serialization at the storage/call boundary.
- **Co-locate what must change together.** Error definitions inside their owning component; configuration types near their consumers rather than in a central grab-bag; code-generation metadata with the types it governs; metadata for a record inside that record rather than a parallel keyed map or positional collection.
- **Trace consumers of anything shared.** When changing a shared capability, interface, or generated data, identify and update every producer and consumer path, and coordinate with dependent implementations rather than leaving them broken or blocked.
- **Don't reuse a check whose semantics differ** from the case at hand; state operation-specific validation explicitly and make caller- or phase-specific behavior explicit in the signature and docs.
- **Record deferred coupling as a tracking issue** that names the intended alternative and the dependency to remove.
